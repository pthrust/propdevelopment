# Список требований для внешней интеграции

## Требования к безопасности

| № | Требование | Обоснование |
|---|---|---|
| 1 | Все данные между PropDevelopment и Платформой Умного дома должны передаваться по TLS 1.3 (или выше) | Защита от перехвата и Man-in-the-Middle |
| 2 | Биометрические данные (шаблоны лиц) не должны передаваться в PropDevelopment. Идентификация происходит на стороне партнёра, PropDevelopment получает только токен события и идентификатор пользователя | Снижение ответственности за ПДн (биометрия — специальная категория) |
| 3 | Webhook-уведомления от партнёра должны содержать HMAC-SHA256 подпись тела запроса, проверяемую smart-gateway | Гарантия, что уведомление отправлено именно партнёром, а не злоумышленником |
| 4 | Логирование всех событий взаимодействия с внешней платформой (успешных и ошибочных) должно храниться в централизованном хранилище с доступом только у ИБ-отдела | Необходимость расследования инцидентов и аудит |
| 5 | Партнёр должен иметь изолированную сетевую зону (DMZ) и не иметь доступа к внутренней инфраструктуре PropDevelopment | Принцип минимального доверия (Zero Trust) |
| 6 | Все API-ключи и секреты для интеграции должны храниться в Vault (HashiCorp Vault или аналоги) и автоматически ротироваться каждые 45 дней | Предотвращение утечки статичных ключей |
| 7 | Должна быть реализована проверка допустимых IP-адресов для входящих webhook'ов (белый список CIDR партнёра) | Дополнительный уровень защиты от спуфинга |
| 8 | Партнёр обязан предоставить SLA по времени отклика (не более 2 секунд на операцию управления) и коэффициент доступности 99.6% | Бизнес-требование: «Умный дом» должен работать без задержек |

## Протоколы аутентификации и авторизации

| Компонент | Протокол | Описание |
|---|---|---|
| Мобильное приложение → tenant-core | OAuth 2.0 / OIDC (через Keycloak) | Пользователь авторизуется в приложении, получает Access Token (JWT) с ролями |
| tenant-core → smart-gateway | OAuth 2.0 Client Credentials | tenant-core выступает как доверенный клиент, получает токен для вызовов к smart-gateway. Это внутренний контур |
| smart-gateway → Платформа Умного дома | OAuth 2.0 Client Credentials + API Key | smart-gateway использует свои учётные данные (client_id + client_secret), получает токен у партнёрского Auth Server. В некоторых запросах может добавляться API Key в заголовок |
| Платформа Умного дома → smart-gateway (webhook) | HMAC-SHA256 подпись | Тело запроса подписывается секретным ключом, smart-gateway пересчитывает подпись и сравнивает. Дополнительно проверяется время запроса |

## Взаимодействие между системами предприятия и внешней платформой

### Синхронное взаимодействие (команды управления)

1. Собственник открывает мобильное приложение → нажимает «Открыть калитку»  
2. mobile-app отправляет POST /api/smart/gates/open на tenant-core  
3. tenant-core:  
- Проверяет JWT и права пользователя на это действие  
- Вызывает smart-gateway с командой: POST /api/v1/devices/{deviceId}/command  
4. smart-gateway:  
- Проверяет кэш прав (если есть) или обращается к tenant-core-db за актуальными правилами  
- Формирует запрос к внешней платформе (аутентификация Client Credentials)  
- Отправляет команду  
- При получении ответа обновляет статус в кэше и возвращает успех/ошибку в tenant-core  
5. tenant-core логирует событие и отправляет уведомление в DWH  

### Асинхронное взаимодействие (события)

1. Посетитель звонит в домофон  
2. Платформа Умного дома распознаёт лицо (биометрия) или выполняет классический звонок  
3. Платформа отправляет webhook на smart-gateway:  
- Для звонка: { "event": "call", "deviceId": "...", "visitorId": "...", "timestamp": "..." }  
- Для распознавания: { "event": "recognized", "deviceId": "...", "userId": "...", "confidence": 0.98 }  
4. smart-gateway:  
- Проверяет HMAC-подпись и время запроса  
- Декодирует событие  
- Если событие «recognized» — проверяет, разрешён ли доступ этому пользователю (кэш)  
- Если доступ разрешён — отправляет команду на открытие двери (синхронно через REST) или возвращает успех  
- Если доступ не разрешён — уведомляет владельца через push-уведомление (через tenant-core и Firebase)  
5. tenant-core сохраняет событие в БД и отправляет в DWH для аналитики
